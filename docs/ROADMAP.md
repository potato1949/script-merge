# 后续版本开发方向

分三档：「近期」按顺序做；「暂缓」是有价值但目前不急的，有实际需要再提上来；「明确不做」是已确认的取舍。每项标了大致工作量（小 = 半天内，中 = 一两天，大 = 需要先做设计）。

实现细节和现有架构见 [DEVELOPMENT.md](DEVELOPMENT.md)。

## 近期（按顺序）

### 1. 模板内容可直接编辑（中）

**现状**：「模板」页里，策略组模板和规则模板只能改名和删除；要改内容得套用到某个订阅组，改好后用同名「存为模板」覆盖。Parser 模板可以直接编辑。

**要做**：

- 模板展开后直接复用订阅组里的策略组编辑器和规则编辑器。`tabGroups` / `tabRules` 目前操作的是 `cur()`（当前订阅组），改成接收任意带 `groups` / `ruleSets` 字段的对象即可同时服务模板；规则编辑器里的策略候选列表（`policyNames`）对规则模板没有对应的策略组可取，需要退化为自由输入。
- 完成后，模板的编辑和**新建**都放在「模板」页里完成（三类模板都能从空白新建），不再依赖「套用 → 修改 → 另存覆盖」的绕路。订阅组里的「存为模板」随之去掉，模板只在「模板」页创建和修改。

### 2. 模板与订阅组的差异提示（小）

依赖第 1 项：模板能直接改之后，「模板更新了、哪些组没跟上」才是常见情况。

**问题**：模板是复制语义，套用之后就不知道某个订阅组「还是不是模板原样」。模板更新后，也不知道哪些组该重新套用。

**要做**：订阅组记下最近一次套用的模板 ID 和当时的内容摘要；在策略组 / 规则页显示「来自模板 X，已修改」或「模板 X 有更新，可重新套用」。只做提示，不做自动同步，保持复制语义。

### 3. 上游拉取走代理（小）

**问题**：部署在某些网络环境里，直连拉不到上游订阅。

**要做**：只走环境变量 `HTTP_PROXY` / `HTTPS_PROXY` / `NO_PROXY`，不做界面配置，也不按来源单独配置。

`fetchSubscription` 用的 `http.Client` 没有自定义 `Transport`，落在 `http.DefaultTransport` 上，它本身就会读这几个环境变量（也支持 `socks5://` 地址）。所以主要工作是：补测试确认订阅请求和解锁请求都走代理；启动时在日志里打出生效的代理；README 和 `docker-compose.yml` 里写明用法。以后如果给拉取换了自定义 `Transport`，要记得带上 `Proxy: http.ProxyFromEnvironment`。

### 4. 订阅组之间复用节点来源（中）

**问题**：订阅组彼此完全独立，同一个机场在三个组里要填三遍，改链接也要改三处。已确认「多个组用同一批订阅」是实际用法。

**要做**：把节点来源提升为可被多个订阅组引用的全局对象，订阅组里只保留引用和本组的过滤设置。这会改动数据模型：`configVersion` 加一，`migrate` 里把各组的 `Subscriptions` 提出来（链接、UA 等完全相同的可以合并成一个），并补 `TestMigrateLegacyConfig` 样例。要先想清楚哪些字段属于来源本身（链接、UA 模式、解锁地址、手填节点），哪些属于「某个组怎么用它」（过滤、前缀），以及缓存键是否受影响。

排在导出导入前面，是因为单个订阅组的导出格式取决于这里的数据模型。

### 5. 配置导出与导入（小）

**问题**：改坏了没法回滚，换服务器要手动拷文件。

**要做**：全局设置里导出整份配置为 JSON、从 JSON 导入（导入前走一遍迁移和 `validateConfig`）；另支持单个订阅组的导出导入，方便分享一套配置（导出时去掉订阅链接和令牌，第 4 项之后要连带导出它引用的来源）。

### 6. 访问记录（中）

**问题**：订阅链接泄露了不容易发现；也不知道各个客户端是否在正常更新。

**要做**：记录每个订阅链接最近的拉取（时间、UA、来源 IP、返回了多少节点），在「本组设置」里显示。可选：同一链接出现陌生 IP 时提示。来源 IP 在反向代理后面要读 `X-Forwarded-For`，需要考虑是否信任这个头。

## 暂缓（有需要再说）

### 后台定时刷新（中）

现在只有客户端来拉订阅时才去拉上游，缓存过期后的第一个请求要等所有上游返回。可以按间隔在后台预先刷新缓存；透传 UA 的订阅只刷新近期实际来拉过的「链接 + UA」组合。目前感觉收益不大。

### 节点列表与筛选预览（中）

调「只保留 / 排除」正则和策略组筛选正则时，只能生成整份预览再去 YAML 里找。可以在订阅源展开后查看节点列表，正则输入框旁实时显示命中数量和节点名。

### 节点改名与排序（中）

每个来源可配置改名规则（正则替换）和排序方式。改名在过滤之后、加前缀之前执行。

### 订阅状态一览（小）

剩余流量和到期时间已经从上游拿到了（`Subscription-Userinfo`），但只透传给了客户端。可以在订阅源行上显示已用 / 总流量、到期日期、上次成功拉取时间。

### 更灵活的解锁步骤（中）

解锁目前只是一次 GET，现有上游够用。如果以后遇到需要 POST、带 Referer 或连续访问几个地址的放行页，再改成可配置的请求序列，先确认实际行为再定范围，避免做成通用爬虫。

### 远期方向（大，需要先做设计）

- **输出非 mihomo 系客户端的格式**（Loon 等）：目前只输出 Clash，Stash 可直接使用。方向已定为「上游统一按 Clash 格式拉取，输出时加渲染器转换」，要做的事项见 [CLIENT-SUPPORT.md](CLIENT-SUPPORT.md)。
- **节点可用性检测**：服务器所处网络和客户端不同，服务端测得通不代表客户端能用。可能更适合只做「上游返回的节点数异常变少」这类粗粒度告警。
- **多用户**：需要账号体系和权限隔离，会把个人工具变成小型服务，等有明确需求再考虑。

### 工程与安全

- **验证 Docker 构建**（小）：`Dockerfile` 写好后还没有实际构建过。
- **界面自动化测试**（中）：现在只靠截图人工检查。用无头浏览器跑几条主流程（新建订阅组、套用模板、保存、预览）。
- **会话持久化**（小）：会话存在内存里，重启服务要重新登录。
- **登录保护**（小）：目前只有全局的 1 秒延迟，没有按 IP 限流或锁定。公网部署时值得加。
- **限制服务端访问内网地址**（小）：订阅链接和解锁地址可以填任意 http(s) 地址。公网部署时应拒绝内网和回环地址。
- **清理失效缓存**（小）：订阅被删除或改了链接后，旧缓存文件留在磁盘上，只在同一订阅缓存超过上限时才被淘汰。

## 明确不做

- **CFW Parser 的 JavaScript 形式**（`code` / `file` / `remote`）：需要在服务端执行任意脚本，安全风险和维护成本都高，YAML 形式已覆盖绝大多数用途。
- **模板的引用语义**（改模板自动影响所有套用过的订阅组）：已确认采用复制语义。改一处牵动多处容易出意外，「差异提示」可以解决大部分同步需求。
- **跨 UA 的缓存回退**：已确认某个 UA 拉取失败就是失败，不借用其他 UA 的结果。
- **按地区自动生成策略组**：各机场的节点命名差异很大，自动识别不可靠；现有「按地区分组」模板够用，缺的地区手动加。
