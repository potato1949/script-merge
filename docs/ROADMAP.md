# 后续版本开发方向

按「解决什么问题」组织，每项标了大致工作量（小 = 半天内，中 = 一两天，大 = 需要先做设计）。优先级是当前的判断，随实际使用情况调整。

实现细节和现有架构见 [DEVELOPMENT.md](DEVELOPMENT.md)。

## 近期：把已有功能补完整

这些是现有功能里已知的缺口，用起来会直接碰到。

### 模板内容可直接编辑（中）

**现状**：「模板」页里，策略组模板和规则模板只能改名和删除；要改内容得套用到某个订阅组，改好后用同名「存为模板」覆盖。Parser 模板可以直接编辑。

**要做**：模板展开后直接复用订阅组里的策略组编辑器和规则编辑器。`tabGroups` / `tabRules` 目前操作的是 `cur()`（当前订阅组），改成接收任意带 `groups` / `ruleSets` 字段的对象即可同时服务模板；规则编辑器里的策略候选列表（`policyNames`）对规则模板没有对应的策略组可取，需要退化为自由输入。

### 模板与订阅组的差异提示（小）

**问题**：模板是复制语义，套用之后就不知道某个订阅组「还是不是模板原样」。模板更新后，也不知道哪些组该重新套用。

**要做**：订阅组记下最近一次套用的模板 ID 和当时的内容摘要；在策略组 / 规则页显示「来自模板 X，已修改」或「模板 X 有更新，可重新套用」。只做提示，不做自动同步，保持复制语义。

### 后台定时刷新（中）

**问题**：现在只有客户端来拉订阅时才去拉上游。上游慢，客户端更新就慢；缓存过期后的第一个请求要等所有上游返回。

**要做**：按间隔在后台预先刷新缓存，客户端请求直接命中。透传 UA 的订阅缓存按 UA 区分，只刷新近期实际来拉过的那些「链接 + UA」组合。

### 节点列表与筛选预览（中）

**问题**：调「只保留 / 排除」正则和策略组筛选正则时，只能生成整份预览再去 YAML 里找，反馈慢。

**要做**：订阅源展开后可查看拉到的节点列表；正则输入框旁实时显示命中数量和命中的节点名。策略组的筛选正则同理。

### 订阅状态一览（小）

**问题**：剩余流量和到期时间已经从上游拿到了（`Subscription-Userinfo`），但只透传给了客户端，管理界面上看不到。

**要做**：订阅源行上显示已用 / 总流量、到期日期、上次成功拉取时间；流量将尽或即将到期时标出来。

### 配置导出与导入（小）

**问题**：改坏了没法回滚，换服务器要手动拷文件。

**要做**：全局设置里导出整份配置为 JSON、从 JSON 导入；另支持单个订阅组的导出导入，方便分享一套配置（导出时去掉订阅链接和令牌）。

## 中期：扩大适用范围

### 更灵活的解锁步骤（中）

**问题**：解锁目前只是一次 GET。如果上游的放行页需要 POST、带 Referer、或者要连续访问几个地址，就不够用。

**要做**：解锁改成可配置的请求序列（方法、地址、请求头、请求体）。先确认实际遇到的放行页是什么行为再定范围，避免做成通用爬虫。

### 按地区自动生成策略组（小）

**问题**：「按地区分组」模板是写死的四个地区，机场节点的地区各不相同。

**要做**：根据当前节点名自动识别出现了哪些地区，一键生成对应的测速组并加入节点选择组。

### 节点改名与排序（中）

**问题**：不同机场的节点命名风格混乱，合并后列表很难看；现在只能加前缀。

**要做**：每个来源可配置改名规则（正则替换）和排序方式（按名称、按地区）。改名在过滤之后、加前缀之前执行。

### 订阅组之间复用节点来源（中）

**问题**：订阅组彼此完全独立，同一个机场在三个组里要填三遍，改链接也要改三处。

**要做**：把节点来源提升为可被多个订阅组引用的全局对象，订阅组里只保留引用和本组的过滤设置。这会改动数据模型（需要迁移），做之前先确认「多个组用同一批订阅」是不是常见用法。

### 访问记录（中）

**问题**：订阅链接泄露了不容易发现；也不知道各个客户端是否在正常更新。

**要做**：记录每个订阅链接最近的拉取（时间、UA、来源 IP、返回了多少节点），在「本组设置」里显示。可选：同一链接出现陌生 IP 时提示。

### 上游拉取走代理（小）

**问题**：部署在某些网络环境里，直连拉不到上游订阅。

**要做**：全局或按来源配置 HTTP / SOCKS5 代理。

## 远期：需要先做设计的方向

### 输出其他客户端格式（大）

目前只输出 Clash 格式。sing-box、Surge、Loon、Quantumult X 各有自己的配置格式，规则集和策略组的语义也不完全对应。可以先做 sing-box（用户重合度最高），按订阅链接的参数或客户端 UA 选择输出格式。做之前要明确：策略组和规则在两种格式间哪些能自动转换，哪些要用户分别配置。

### 节点可用性检测（大）

服务端定期测试节点连通性，自动剔除长期不可用的节点。难点在于服务器所处网络和用户客户端所处网络不同，服务端测得通不代表客户端能用，反之亦然。可能更适合只做「上游返回的节点数异常变少」这类粗粒度告警。

### 多用户（大）

现在是单管理员。如果要给家人或朋友各自管理自己的订阅组，需要账号体系和权限隔离。这会改变产品定位（从个人工具变成小型服务），建议等有明确需求再考虑。

## 工程与安全

不直接面向功能，但影响能不能放心用。

- **验证 Docker 构建**（小）：`Dockerfile` 写好后还没有实际构建过。
- **界面自动化测试**（中）：现在只靠截图人工检查。用无头浏览器跑几条主流程（新建订阅组、套用模板、保存、预览）。
- **会话持久化**（小）：会话存在内存里，重启服务要重新登录。
- **登录保护**（小）：目前只有全局的 1 秒延迟，没有按 IP 限流或锁定。公网部署时值得加。
- **限制服务端访问内网地址**（小）：订阅链接和解锁地址可以填任意 http(s) 地址。公网部署时应拒绝内网和回环地址，防止管理密码泄露后被用来探测内网。
- **清理失效缓存**（小）：订阅被删除或改了链接后，旧缓存文件留在磁盘上，只在同一订阅缓存超过上限时才被淘汰。

## 明确不做

- **CFW Parser 的 JavaScript 形式**（`code` / `file` / `remote`）：需要在服务端执行任意脚本，安全风险和维护成本都高，YAML 形式已覆盖绝大多数用途。
- **模板的引用语义**（改模板自动影响所有套用过的订阅组）：已确认采用复制语义。改一处牵动多处容易出意外，上面的「差异提示」可以解决大部分同步需求。
- **跨 UA 的缓存回退**：已确认某个 UA 拉取失败就是失败，不借用其他 UA 的结果。
